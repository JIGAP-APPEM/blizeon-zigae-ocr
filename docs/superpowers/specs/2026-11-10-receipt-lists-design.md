# 영수증 전체 데이터화 설계 (목록 인식 · 기록 JSON · 백업 · 디지털 영수증)

> 작성 2026-11-10 · 상태: 검토 반영, 소유자 승인 대기 · 대상: 「게임 기록 영수증 OCR 도구 — 설계 및 구현 계획서」(이하 계획서)의 명세 변경

이 문서가 승인되면 계획서를 이 문서에 맞춰 고친다. 계획서에 이미 있는 것(서버 없음, 사진 비전송, BYOK AI 재확인, 공개 저장소 규칙, 버전 A.B.CDE, 앱 먼저 진행 순서 등)은 그대로 유지하고, 여기서는 바뀌거나 새로 생기는 것만 적는다.

근거 자료(저장소에 넣지 않음):
- 공개 커뮤니티에 올라온 실물 영수증 사진 3장(각각 사진 6장을 이어 붙인 축소본)을 구간별로 분석한 결과
- 2026-11-10 조사: ML Kit 텍스트 인식, Android 저장·복구, 긴 영수증의 이미지·PDF 출력, 기본 데이터 출처와 라이선스
- 설계 검토(빌더 관점) 질문 8개와 그 답

## 1. 왜 바꾸나

계획서는 "라벨 옆 값 몇 개"를 읽는 구조다. 실물 영수증(블루 아카이브 한국 서버 5주년 페스티벌, 2026-11-07 발행)은 대부분이 반복 목록이다. 학생 약 260명 × 2~3줄, 총력전·대결전 시즌 트로피 약 90줄, 선물 50여 줄, 스토리 진행도 90여 줄 등이다. 지금 구조로는 핵심 데이터를 담을 수 없다.

소유자가 정한 목표:
- **1차:** 영수증의 모든 값을 정해진 구조의 JSON(이하 "기록 JSON")으로 만든다. 다른 출력 양식이 이 JSON을 가져다 쓴다.
- **2차:** 기록 JSON으로 공식 영수증을 그대로(공식 로고·이미지·글자·배치) 디지털로 재현해 이미지와 PDF로 저장한다. 출력 크기는 사용자가 정한다.
- **나중(별도 기능):** 사용자가 출력 양식을 입맛대로 고쳐 저장한다.
- 기록은 앱을 지웠다 다시 설치해도 복구할 수 있어야 한다.

용어:
- **읽기 양식:** 연도별 영수증을 읽는 규칙(계획서의 "템플릿", `public/templates/<id>.json`).
- **출력 양식:** 기록 JSON을 그리는 규칙(2차 목표의 공식 영수증 재현 양식, 나중의 사용자 양식).
- **기본 데이터(사전):** 학생·선물·보스·스토리 이름처럼 고정된 데이터. 앱에 내장하고 기록 JSON과 섞지 않는다.
- **기록 계약:** 기록 JSON `data`의 고정된 모양(5.1).

## 2. 목표 · 하지 않을 것 · 실패로 볼 것

### 목표
- 영수증의 모든 섹션(4장)을 기록 JSON에 담는다.
- 이름은 기본 데이터에서 찾아 그 표기를 쓴다. 사전으로 정할 수 없는 이름은 인쇄된 모양을 보관한다.
- 수천 개 값 중 확인이 필요한 것만 사용자에게 보인다.
- 기록을 여러 개 보관한다(목록·열기·삭제). 내년 영수증, 같은 영수증을 다시 찍은 것, 다른 계정의 영수증이 모두 별개 기록이다.
- 기록 JSON을 기기의 공용 다운로드 폴더에도 사본으로 저장하고, 재설치 뒤 파일을 골라 복구한다.
- (2차) 공식 영수증 재현 이미지(여러 장)와 PDF를 만든다.

### 하지 않을 것 (이번 범위 밖)
- 사용자 맞춤 출력 양식 편집 (나중 별도 기능)
- 글꼴 선정 (소유자가 나중에 정한다)
- 서버, 계정, 클라우드 동기화, Android 자동 백업(Google Drive)
- 사진 순서 자동 판별
- 게임 규칙으로 값 검증하기 (예: `Lv. 1`인데 고유 무기가 있는 기록이 실제로 인쇄되어 있다. 영수증이 정답이다)
- CSV 내보내기 (목록이 겹겹이 들어간 구조라 맞지 않는다. 계획서의 CSV 항목은 뺀다)
- 행 패턴(정규식)을 자동으로 만들어 주는 화면 (6.8)

### 실패로 볼 것
- 애매한 이름을 조용히 다른 이름으로 바꿔 넣는 것 (`미카`↔`미나`, `세리카`↔`세리나` 등)
- 사진 사이에 빠진 줄이 있는데 아무 경고 없이 끝나는 것
- 해석하지 못한 줄을 말없이 버리는 것
- 사용자가 고친 값이 다시 계산할 때 다른 행에 붙거나 말없이 사라지는 것
- 같은 이름의 서로 다른 행(이벤트 복각 등)을 하나로 합쳐 버리는 것
- 닉네임이나 서클명이 사용자가 모르게 기기 밖(AI 요청, 공유 파일)으로 나가는 것

## 3. 제약 (계획서 「전역 제약」에 더하거나 바꾸는 것)

- **공식 로고·이미지 (변경):** 사용자 정보가 전혀 없는 부분만 잘라 공개 저장소에 넣고 재현 출력에 쓴다. 계획서 Task 5.3의 "게임 공식 로고와 이미지는 넣지 않는다"를 이 문장으로 바꾼다. 커밋 차단 훅의 이미지 허용 경로에 그 폴더(`public/receipt-art/`)를 추가한다.
- **개인 식별 칸:** 닉네임, 현재 가입 서클 두 칸과 교무일지 첫 문단의 닉네임이 `private`이다. AI 재확인으로 보내지 않고, 공유·출력에는 가리기 옵션을 둔다.
- **기본 데이터 커밋:** SchaleDB에서 변환한 기본 데이터는 소유자가 사용 허락을 확인하기 전까지 저장소에 커밋하지 않는다(5.4).
- **Android 최소 버전:** minSdk 29 (Android 10).
- **APK:** arm64-v8a·armeabi-v7a만 담은 APK 하나 (번들 한국어 모델이 ABI당 약 4 MB).
- **자동 백업 끔:** `android:allowBackup="false"`, Android 12+용 `dataExtractionRules`도 모두 제외.
- **실기기 기준:** 샤오신 2024 (Android 13+, 약 4 GB RAM, 구글 서비스 있음).
- **앱 공개 조건:** 원본 해상도 영수증 사진으로 실측(10장)을 마치기 전에는 앱을 공개 릴리스하지 않는다.

## 4. 실물 영수증 구조 (2026 · 한국 서버 · 5주년)

샘플은 게시용 축소본이라 글자 높이가 6~9px이다. 표기가 불확실한 곳은 (확인 필요)로 적었다. 원본 해상도 사진으로 섹션 순서와 표기를 확정해야 한다(10장).

### 4.1 공통 레이아웃
- 세로로 긴 감열지. 사진 한 장에 약 65~70줄.
- 줄 종류:
  - **큰 헤더:** 검은 상자에 흰 글씨 (`나의 학생부 기록`, `나의 최애 학생 기록`, `나의 학생들과의 생활 기록`, `나의 집무실 기록`, `나의 재화 기록`, `2026년도 교무일지`)
  - **작은 헤더:** 값 없는 일반 글씨 (`총력전 역대 트로피`, `선물 사용 횟수` 등)
  - **글머리 행:** `• 라벨`(왼쪽) + 값(오른쪽 정렬), 라벨과 값 사이 간격이 넓다
  - **단일 행:** `라벨  값` (글머리 없음)
  - **이름 줄:** 학생부 레코드의 첫 줄
  - **문단:** 교무일지
  - **장식:** 로고, 이중 점선
- ML Kit이 넓은 간격의 한 행을 한 줄로 줄지 두 덩어리로 줄지는 문서화되어 있지 않다. 그래서 행을 다시 조립한다(6.2).

### 4.3 학생부 레코드
```
<이름>[(<복장>)] (Lv. <레벨>, <성급>성[ 고유 무기 <무기>성])
  • 스킬 성장        EX. <v> / <v> / <v> / <v>
  • 모모톡 진행도    모모톡 인연스토리 EP <n> 완료      ← 없는 레코드가 많다(샘플에서 약 25%)
```
- `<v>`는 `MAX` 또는 `Lv. N`. 세 번째 칸만 `Lv.N`(공백 없음)으로 인쇄된다.
- 성급 1~5. 2~4성은 고유 무기 부분이 없다. 5성이어도 고유 무기가 없을 수 있다.
- 정렬: 뒷부분은 "고유 무기 성급 묶음 안에서 가나다순"으로 보이나 앞부분은 이 규칙을 따르지 않는다. 순서는 인쇄된 대로 보관한다.

### 4.4 교무일지
- 고정 문장에 값 칸이 끼워진 형태다. 칸: 닉네임(private), 함께한 햇수, 올해 스케줄 횟수, 끝까지 읽은 이야기 수, 마지막 이야기(`『스토리 - 에피소드』`), 가장 빛난 전장(보스), 총력전 누적 점수, 대결전 누적 점수, 제약해제결전 최고 단계, 종합전술시험 최고 점수, AP, 직접 지휘 횟수, 소탕 횟수, 새 학생 수, 처음 인사한 학생, 최근 학생, 가장 많이 건넨 선물, 그 횟수, 크레딧, 청휘석, 연도.
- 값 뒤 조사가 받침에 따라 바뀐다(`이고/고`, `이에요/예요`). 따옴표는 `『』`(닉네임·이야기)와 `「」`(선물) 두 종류.
- 줄바꿈은 고정 줄바꿈과 약 30자 자동 줄바꿈이 섞여 있다.
- 값은 "올해" 값이라 목록의 누적값과 다르다. 따로 저장한다.

### 4.5 이름 표기 (기본 데이터 설계에 필요한 사실)
- 학생: 복장 괄호 앞 공백 없음(`하나코(수영복)`), 괄호 없는 변형(`시로코*테러`), 공백이 든 콜라보 이름(`사텐 루이코`, `쇼쿠호 미사키`). 복장 20여 종. 같은 기본 이름의 변형이 여러 개다.
- 한 글자 차이 이름이 많다: 세리카–세리나, 하나코–하나에, 히나–히나타, 하루나–하루카, 아즈사–카즈사, 미사키–키사키, 미도리–미노리, 마리–마리나, 아카네–아카리, 노노미–노조미, 미나–미카.
- 보스: 총력전·대결전은 `보스(지형)` (지형: 시가전·야전·실내전), 제약해제결전은 `보스 (장갑)`.
- 약 18자를 넘는 이름은 `...`로 잘린다. 지형까지 잘리는 행(`KAITEN FX Mk.0(...`)도 있다.
- 감열지 인쇄가 흐려 비슷한 글자가 섞인다(8/9, 도/모, 카/키, 성/신).

## 5. 데이터 구조

### 5.1 기록 계약
- 기록 JSON의 `data`는 **공통 코드(core)에 고정된 계약**이다. TypeScript 타입(`src/core/record.ts`)과 JSON Schema(`public/schema/record.schema.json`)로 정의한다.
  - 연도별 읽기 양식은 자기 섹션과 값을 이 계약의 키에 맞춘다. 읽기 양식의 섹션 `key`와 값 이름은 계약에 있는 것이어야 하고, check-templates가 대조한다.
  - 새 영수증에 계약에 없는 내용이 생기면 계약을 고치고 `schemaVersion`을 올린다(이때는 읽기 양식 파일만으로 끝나지 않고 코드 변경이 필요하다).
  - 출력 양식은 연도와 상관없이 이 계약만 읽는다.
- 기록마다 `recordId`(첫 저장 때 앱이 만드는 UUID)가 있다. 앱은 기록을 여러 개 보관한다.
- **이름 값**은 `{ "printed": string, "ref": string | null }`.
  - `ref`: 일치한 기본 데이터 항목의 id. 찾지 못했거나 잘려서 하나로 정할 수 없으면 `null`.
  - `printed`: 재현에 쓰는 표기.
    - 사전과 확실히 맞았거나(`ok`) 사용자가 후보를 고르면 사전의 `name`이다.
    - 잘린 이름이 하나로 정해지면 사전 표기를 인쇄된 길이에서 자르고 `...`를 붙인다.
    - 그 밖에는 정리한 OCR 문자열(공백 정리, OCR 혼동 교정 후)이다.
  - 데이터용 출력은 `ref`로 기본 데이터의 이름을, 재현 출력은 `printed`를 쓴다.
- 숫자는 숫자로, `MAX`는 문자열 `"MAX"`로 둔다.
- 인쇄되지 않은 줄은 `null`이다(예: 모모톡 줄이 없으면 `momotalkEp: null`). `0`과 구분한다.
- 목록은 **인쇄 순서 그대로의 배열**이다. 같은 이름이 두 번 나와도 별개 행이다.
- 값의 확인 상태는 `review` 맵에, 해석하지 못한 행은 `unparsed`에, 사용자 수정은 `corrections`에 둔다. 출력 양식은 `data`만 읽으면 된다.

### 5.3 읽기 양식 확장
계획서의 `Template.fields`(라벨 → 값)는 그대로 두고, 영수증 순서대로 `sections`를 더한다. 섹션 `key`와 `values`의 이름은 기록 계약의 키다.

```ts
type SectionSpec =
  | { key: string; kind: 'fields'; header?: string; fields: FieldSpec[] }        // 단일 값 묶음 (기존 방식)
  | { key: string; kind: 'list'; header: string; rows: RowSpec[] }               // 글머리 행 목록
  | { key: string; kind: 'records'; header: string; start: RowSpec; parts: RowSpec[] } // 학생부처럼 여러 줄 레코드
  | { key: string; kind: 'ranking'; header: string; row: RowSpec }               // 최애 순위 (줄 넘김 이어 붙이기)
  | { key: string; kind: 'letter'; header: string; sentences: SentenceSpec[] };  // 교무일지

interface RowSpec {
  pattern: string;                          // 이름 붙은 그룹이 있는 정규식. 행 재조립·정규화 뒤의 텍스트에 적용
  values: Record<string, ValueSpec>;        // 그룹 이름 → 값 해석 (이름은 기록 계약의 키)
}
interface ValueSpec {
  type: 'number' | 'text' | 'date' | 'datetime' | 'duration' | 'enum' | 'skill' | 'name';
  dict?: string;          // type 'name'일 때 기본 데이터 파일
  enum?: string[];
  list?: boolean;         // 쉼표로 나뉜 여러 이름 (최애 순위)
  private?: boolean;
  range?: [number, number];
}
interface SentenceSpec { pattern: string; values: Record<string, ValueSpec> } // 조사 변이(이고/고, 이에요/예요)를 패턴이 받는다
```
- 섹션 머리말은 `header`를 퍼지 비교(LABEL_MIN_SIM)로 찾는다.
- `records`: `start`가 맞는 행이 새 레코드를 연다. `parts` 중 하나가 맞는 행은 현재 레코드에 붙는다. 같은 part가 두 번 나오면 경고.
- `ranking`: 줄이 넘어간 순위 행은 코드의 버퍼 규칙으로 앞 행에 공백 없이 이어 붙여 해석한다(계획서 Task 1.11).
- 읽기 양식 최상위의 `ignore`(정규식 목록)에 맞는 행은 데이터가 없는 행으로 건너뛴다(점선, 안내 줄, 로고 글자, 꼬리 문구, 대응 섹션 없는 큰 헤더).
- 머리말 없는 `fields` 섹션은 그 필드 라벨이 나오면 그 섹션으로 넘어간다(목록 바로 뒤에 오는 횟수·소모량 묶음).
- 패턴은 OCR 잡음(쉼표↔마침표, 공백 누락, `/`↔`|`, `성`↔`신`)을 받아들이도록 쓴다.
- 스키마 검증(validate.ts)과 check-templates가 `sections`도 검사하고, 섹션·값 이름을 기록 계약과 대조한다.

### 5.4 기본 데이터 (사전)
- 앱에 내장한다(`public/dict/*.json`). 계획서의 원격 갱신(Cloudflare Pages)은 유지한다.
- 항목: `{ "id": string, "name": string, "aliases"?: string[] }`. `name`은 **영수증 인쇄 표기 그대로**다(예: `하나코(수영복)`, `시로코*테러`, `비나(시가전)`, `세트의 분노 (특수장갑)`).
- 파일: `students`, `gifts`, `bosses`(총력전·대결전 보스+지형 조합), `limitBreak`(제약해제결전 보스+장갑), `mainStories`, `events`, `miniStories`, `groupStories`(스토리는 목록마다 다른 파일), `collabItems`.
- id는 한번 정하면 바꾸지 않는다(기록 JSON의 `ref`가 가리킨다).
- **출처 (소유자 결정):** SchaleDB 한국어 데이터(`schaledb.com/data/kr/*.json`)에서 시작한다.
  - 변환 스크립트(`scripts/import-schaledb.mjs`)가 학생·선물·레이드를 가져와 영수증 표기에 맞춘다. 지형 `시가지/야외/실내` → `시가전/야전/실내전`, 장갑 표기, 같은 이름의 중복 항목 합치기(예: `호시노(무장)` 2건)를 처리한다.
  - 한국 서버(Global) 출시 학생만 넣는다.
  - 소유자가 사용 허락을 확인하기 전까지 변환 결과는 로컬에만 두고 커밋하지 않는다. 확인 뒤 커밋할 때 THIRD_PARTY_NOTICES에 출처를 적는다.
  - 참고: SchaleDB 저장소에는 라이선스 파일이 없고, 운영자가 이슈에서 조건부로 재사용을 허용했다(게임에 없는 번역은 번역자 허락 필요). 게임 추출 데이터(electricgoat/ba-data)는 쓰지 않는다.
- 스토리 제목은 공개 데이터에 거의 없어서, 영수증에서 모아 손으로 관리한다(템플릿 제작 도구가 후보를 모아 준다).

### 5.5 이름 매칭 규칙
- 비교 전 정규화: 공백 정리, `(` 앞 공백 무시, 라틴 소문자화. 이름 안의 공백 유무만 다른 두 항목은 기본 데이터에 없다고 가정한다(검증 스크립트가 확인).
- 점수는 계획서의 자모 유사도.
  - 1등 후보 점수 < `DICT_MIN_SIM`: `ref: null`, `review` + `not_in_dict`.
  - 점수 ≥ `DICT_MIN_SIM`: `ref`를 채운다.
  - 점수 ≥ `DICT_OK_SIM` **그리고** 2등 후보와의 차이 ≥ `DICT_MARGIN`(초기값 0.1): `ok`. 아니면 `review` + `dict_ambiguous`.
- 잘린 이름(`...` 또는 `…`로 끝남): 남은 앞부분과 앞부분이 맞는 항목만 후보로 한다. 하나면 `ref`를 채우고, 여럿이면 `ref: null` + 사유 `truncated`(상태는 `ok`. 인쇄 자체가 그렇고 사용자가 고칠 것이 없다).
- 후보 제한: 최애 순위와 교무일지의 학생 이름은 학생부에서 찾은 학생 중에서 먼저 찾는다.
- 학생부에서 두 레코드가 같은 `ref`로 가면 둘 다 `review` + `duplicate_ref`.
- 확인 화면은 `dict_ambiguous`·`not_in_dict` 칸에 상위 후보 3개를 보여 주고 고르게 한다.

## 6. 처리 흐름 (계획서 대비 변경)

### 6.1 입력과 사진 순서
- 문서 스캐너(페이지 순서) 또는 사진 고르기(선택 순서). 주어진 순서를 쓰고, 썸네일을 끌어서 순서를 바꿀 수 있다.
- 사진마다 가져올 때 바뀌지 않는 `photoId`를 붙인다(순서를 바꿔도 그대로).
- 촬영 안내: "영수증을 위에서부터 차례로, 위아래가 한두 줄씩 겹치게 찍어 주세요."

### 6.2 행 재조립 (core, 새 함수)
- `assembleRows(lines: OcrLine[]): Row[]` — 사진별로 세로 중심이 `ROW_OVERLAP` 안에서 겹치는 OcrLine을 한 행으로 묶고, x 순서로 이어 붙인다. 엔진이 한 행을 몇 덩어리로 주든 결과가 같아야 한다.
- `Row = { rowKey, text, parts: OcrLine[], photoId, y, score }`.
  - `rowKey`는 `photoId`와 그 사진 안의 행 순번으로 만든다(예: `p3:r41`). 같은 사진을 다시 처리해도 같은 값이 나와야 한다.
  - `score`는 parts의 최소 score.
  - 원본 조각 미리보기와 AI 재확인 조각은 parts의 박스를 합친 영역을 쓴다.
- 허용오차는 실제 사진으로 잰 뒤 정한다(10장). 그 전에는 계획서의 `ROW_OVERLAP` 초기값을 쓴다.

### 6.3 사진 이어 붙이기 (core, 새 함수)
- `mergePhotos(rowsPerPhoto: Row[][]): { rows: Row[]; seams: Seam[] }` — 이웃한 두 사진에서 앞 사진의 끝 행들과 뒤 사진의 첫 행들이 가장 길게 겹치는 구간을 찾아(정규화 텍스트 유사도 기준, 1행 이상), 뒤 사진의 겹친 행을 뺀다.
- 이름(키)으로 합치지 않는다. 같은 이름의 다른 행이 있기 때문이다.
- 겹친 행의 읽기가 서로 다르면 score가 높은 쪽을 쓰고, 정규화한 값이 다르면 `review` + `conflict`.
- 겹침을 찾지 못한 이음매는 `seam_no_overlap` 경고가 된다.
- 계획서의 `dedupeLines`(같은 사진 안 타일 겹침)는 그대로 쓰고, 이 함수는 사진 사이를 다룬다.

### 6.4 섹션 나누기와 행 해석 (core)
- `parseReceipt(t: Template, rows: Row[], dicts: Dicts, corrections: Correction[]): { data, review, warnings, unparsed, staleCorrections }` — 합친 행을 차례로 보며 섹션 머리말이 나오면 현재 섹션을 바꾸고, 그 섹션의 규칙으로 행을 해석한다.
- 어떤 규칙에도 맞지 않는 행은 버리지 않고 `unparsed`(rowKey, 섹션, 텍스트, 사진)로 남긴다.
- 계획서의 `extractFields`(단일 값)는 `kind: 'fields'` 섹션 안에서 재조립된 행에 대해 쓴다.

### 6.5 빠진 줄 감지 (경고만, 막지 않음)
- 겹침 없는 이음매 (6.3)
- 학생부 레코드 수 ≠ 기본 정보의 `함께한 학생 수`
- 시즌 번호가 이어지지 않음 (총력전, 대결전, 제약해제결전)
- 선물 횟수가 내림차순이 아님
- 이름 줄은 있는데 스킬 줄이 없는 레코드
- 경고는 위치(섹션, 사진 번호)와 함께 확인 화면 맨 위에 보이고, 사진을 더 찍어 넣으면 다시 계산한다.

### 6.6 확인 화면과 사용자 수정
- `review`·`missing` 값, `unparsed` 행, 경고만 섹션별로 모아 보인다. 섹션마다 남은 개수를 표시한다.
- **값 수정:** 고친 값은 `corrections`에 `{ rowKey, value(계약의 값 경로), set }`로 저장한다. 배열 위치가 아니라 원래 행(`rowKey`)에 묶는다. 고친 값은 해당 ValueSpec으로 다시 정규화하고 사유에 `edited`를 넣는다.
- **해석 못 한 행:** 사용자가 행 텍스트를 고치면 그 섹션 규칙으로 다시 해석해 데이터에 넣는다. 이 수정도 `corrections`에 `{ rowKey, text }`로 저장한다. 그래도 남은 행은 `unparsed`로 기록 JSON에 저장한다.
- **다시 계산:** 사진을 더하거나 순서를 바꾸면 행 재조립부터 다시 하고, `corrections`를 `rowKey`로 다시 입힌다. 원래 행을 찾지 못한 수정은 버리지 않고 `staleCorrections`로 확인 화면에 "적용하지 못한 수정"으로 보인다.

### 6.7 AI 재확인
- 계획서 원칙 그대로. 목록 행은 행 영역을 잘라 보낸다. `private` 값과 그 값이 든 행(기본 정보의 닉네임·서클 행, 교무일지 첫 문단)은 보내지 않는다.

### 6.8 템플릿 제작 도구 (계획서 Task 3.2 범위)
- 행 패턴(정규식)은 사람이 읽기 양식 JSON에 직접 쓴다(AI 도우미 사용 가능).
- 도구는 앱이 내보낸 인식 줄 파일을 불러와 다음을 한다: 읽기 양식으로 해석한 결과 미리보기, `unparsed` 행 강조, 섹션별 행 수와 경고 표시, 사전에 없는 이름 후보(새 스토리 제목 등) 모으기와 사전 파일 형식으로 내보내기.
- 예시 행을 골라 패턴을 만들어 주는 화면은 만들지 않는다.

## 7. 저장과 복구
- **기본 저장:** 기록 JSON을 앱 전용 저장소(IndexedDB)에 `recordId`로 둔다. 진행 중 세션 저장(계획서 Task 2.3)과 별개로, 확인을 마친 기록을 저장한다.
- **기록 목록:** 첫 화면에 기록 목록(읽기 양식 연도, DATE, 저장 시각)과 열기·삭제·새로 읽기.
- **다시 고치기:** 기록마다 인식 줄(OCR 텍스트만, 이미지 없음)을 기기 안에 따로 보관해, 저장한 기록을 열어 확인 화면에서 다시 고칠 수 있다. 인식 줄은 백업 파일에 넣지 않으므로, 백업에서 복원한 기록은 읽기 전용이다.
- **사본:** 저장할 때마다 기록 JSON을 MediaStore로 `Download/<앱 폴더>/receipt-<recordId>.json`에 쓴다. 권한이 필요 없다(Android 10+). 같은 기록은 같은 파일을 덮어쓴다. 재설치 뒤에는 이전 파일을 덮어쓸 수 없으므로 새 파일이 생긴다(이전 파일은 사용자가 정리).
- **복구:** 첫 화면과 설정에 「백업에서 복원」. 시스템 파일 선택기(`ACTION_OPEN_DOCUMENT`, `application/json`, 여러 개 선택 가능)로 고르면 파일마다 `schemaVersion`과 기록 계약 스키마로 검사한 뒤 가져온다. 같은 `recordId`가 이미 있으면 덮어쓸지 묻는다. 재설치한 앱은 이전 파일을 혼자 읽을 수 없으므로 이 선택이 꼭 필요하다.
- **플러그인:** 기존 Java 플러그인에 `saveToDownloads({ name, text })`와 `openDocuments({ mimeTypes, multiple })`를 추가한다. 서드파티 플러그인은 쓰지 않는다.
- **자동 백업 끔:** 3장 참고. 기록이 사용자 모르게 Google 서버로 복사되지 않게 한다.
- 다운로드 폴더의 사본에는 닉네임·서클이 들어 있다(사용자 기기 안이다). 공유용 내보내기에는 가리기 옵션을 둔다.

## 8. 디지털 영수증 (2차 목표)
- **순서 (소유자 결정):** 앱 공개 다음, 웹 버전보다 먼저.
- **이번 계획의 범위:** 진행 순서에 단계 자리만 잡는다. 상세 계획은 글꼴과 공식 이미지 조각이 정해진 뒤 따로 쓴다. 출력 양식을 데이터 파일로 할지 연도별 코드로 할지도 그때 정한다.
- 정해 둔 방향:
  - **입력:** 기록 JSON(기록 계약) + 출력 양식 + 공식 이미지 조각(`public/receipt-art/<연도>/`, 사용자 정보가 없는 부분만).
  - **그리기:** HTML/CSS로 영수증을 배치하고, 줄 경계에서 자른 조각을 차례로 캔버스에 그려 PNG/JPEG 여러 장으로 저장한다. 조각 하나를 그리고 인코딩하고 해제한 뒤 다음 조각으로 넘어간다. 캔버스 한 변 한계(32,767px) 때문에 한 장짜리는 만들 수 없다. 조각 높이 기본값 8,192px(저사양 기기 기준), 폭은 사용자가 고른다.
  - **PDF:** 같은 이미지 조각을 PDF 쪽으로 넣는다(벡터 PDF는 하지 않는다).
  - **원문 재현:** 이름은 `printed`를 쓴다. 교무일지는 문장 양식에 값을 넣고 조사 규칙과 줄바꿈 규칙(고정 + 약 30자)을 재현한다.
  - **글꼴:** 소유자가 나중에 정한다. 앱에 넣어 배포하려면 OFL 같은 무료 라이선스여야 한다(후보 메모: Noto Sans KR, Pretendard, 나눔고딕코딩, Gowun Dodum).
  - **저장:** MediaStore(이미지는 Pictures, PDF는 Download).
  - 닉네임·서클 가리기 옵션.

## 13. 이 설계에서 내린 판단 (확인용)

소유자 결정:
- 기록은 여러 개 보관
- 기본 데이터는 SchaleDB에서 시작, 사용 허락은 소유자가 확인 (확인 전 커밋 금지)

- 공식 로고·이미지는 사용자 정보 없는 부분만 공개 저장소에

typesafe-ai(Jev)에 맡겨 정한 것:
- 사진 순서는 주어진 순서 + 사용자가 바꾸기 (자동 판별 안 함)
- 이름은 `printed` + `ref` 둘 다 저장, `printed`는 확실하면 사전 표기
- 백업은 다운로드 폴더 사본 + 파일을 골라 복구, 자동 백업 끔
- 저장·열기 기능은 기존 Java 플러그인에 추가
- minSdk 29
- APK는 ARM 두 종만 담은 단일 APK
- PDF는 이미지 조각을 쪽으로 넣는 방식
- 사용자 수정은 원래 행에 묶어 다시 계산 뒤 다시 입힘
- 기록 계약은 core에 고정, 읽기 양식이 계약에 맞춤
- 해석 못 한 행은 고쳐서 다시 해석할 수 있고, 남은 것은 기록에 저장
- 템플릿 제작 도구는 미리보기·unparsed 강조·사전 후보 모으기까지 (패턴 자동 생성 없음)
- 백업 파일 검증은 Ajv standalone으로 미리 만든 검증 코드 (계획 작성 중 결정)
- 순위 줄 넘김은 코드의 버퍼 규칙, 무시할 행 목록은 읽기 양식 최상위 `ignore` (계획 검토 중 결정)

typesafe-ai 답을 작성자가 뒤집은 것 (확신이 낮았던 두 건, 계획 검토 중):
- 스토리 종류 구분: kind 필드(0.6) 대신 목록마다 사전 파일을 나눔 — 새 필드와 거르는 코드 없이 섹션이 자기 파일만 가리키면 된다
